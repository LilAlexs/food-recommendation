# v4：确认菜谱身份与隔离正文

这是针对已安装 v3 的增量补丁。先备份本地代码，再合并包内目录，替换同名文件。保留原数据目录、.env、主Compose和前端。本包不包含密钥，不修改数据库或重建向量索引。

## 现在会发生什么

- “宫保鸡丁怎么做？”：精确确认，加载该菜谱的单份Markdown原文，生成时不再混入干煸仔鸡。
- “麻婆豆腐怎么做？”：同样只读取麻婆豆腐原文，不把凉拌豆腐作为目标正文。
- “番茄炒蛋需要哪些材料？”：经审核别名映射到“西红柿炒鸡蛋”。别名文件 recipe_aliases.json 可以维护，但不能把只是相似的菜当同义词。
- “清蒸鱼怎么做？”：提示选择清蒸鲈鱼或清蒸鳜鱼；不会自动替用户选鱼种。
- “红烧肉怎么做？”：库内有多个具体版本，列出选择。用户回复“查看菜谱：简易红烧肉”后再生成。
- “火星麻婆豆腐怎么做？”：提示“未收录或未识别到”，相似结果只作为需要确认的建议，不进入生成模型。
- “宫保鸡丁和麻婆豆腐怎么做？”：请用户一次指定一道菜，避免混合步骤。
- “今天晚餐吃什么？”等推荐/关系查询：保留v3原有GraphRAG路由，不强行套单菜确认。

当前前端无需改动：提示与选项作为现有chunk文本显示，用户复制“查看菜谱：菜名”回复。普通JSON及SSE也附带recipe_status、answer_source、source、recipe_id或options元数据，方便以后做按钮。当前没有做可点击按钮、没有开放“回复数字自动选择”，也没有实现通用模型/外部搜索兜底，不会展示无法执行的兜底选项。

## 为什么用本地Markdown

之前的Trace只有候选菜名/节点ID，未包含完整正文，不能确定数据库里是否已出现菜名与步骤错配。上传项目中的 data/dishes 原文可以确认对应菜谱，所以v4先用它作为已确认单菜的可信来源，绕过混杂的图/向量候选，而不是只按可能错误的metadata过滤。

这是一条明确的本地菜谱精确查找分支，不是GraphRAG所有检索的替代，也不宣称已经修复Neo4j/Milvus的存储关联。通用推荐与关系查询仍走原系统，需要另行验证质量。

目录索引要求顶层菜名标题与文件名一致，并存在操作/步骤章节。每份使用 local: 前缀的稳定路径哈希ID（不是现有Neo4j/Milvus ID），同时记录原文sha256及相对来源路径。取文时再核对原文版本，源文件改变或不可读返回资料不可用，不回退到其他菜。

当前附件检查得到319个唯一规范名称；另有两份标题/文件名不一致的文档被隔离（酒酿醪糟、豉汁蒸白鱔食谱），请求这些名称会提示资料暂不可用，不冒充未收录。部分没有标准操作章节的文档未纳入索引。这是目录覆盖边界；“未收录或未识别”不等同于已证明整个数据库没有该菜。

## 应用

复制替换后，在PowerShell项目根目录执行（保持v3两个开关开启）：

```powershell
$env:RAG_ADAPTIVE_CONTEXT="1"
$env:RAG_FAST_SIMPLE_QUERY="1"
$env:RAG_RECIPE_GUARD="1"
docker-compose -f docker-compose.yml -f compose.llm-diagnostics.yml -f compose.optimizations.yml -f compose.recipe-identity.yml up -d --no-deps --force-recreate backend
```

无新增第三方依赖；现有rag_modules、data挂载已覆盖新代码与别名JSON，不需要pull/build。重建清空内存会话/缓存，数据库卷保留。等待 /health 可访问再操作。不要 down -v。

守卫默认开启（未设置RAG_RECIPE_GUARD时为1）。设0仅用于隔离实验，会恢复v3单菜路径及其已知混用风险，不建议正常使用时关闭。目录/别名在进程内缓存，修改数据、别名或配置后重建/重启后端加载新版本。

## 先在网页验证

新建会话，依次尝试：

1. 宫保鸡丁怎么做？——应使用包含花生的宫保鸡丁原文，不出现干煸仔鸡的土豆复炸步骤。
2. 麻婆豆腐怎么做？——应使用麻婆豆腐原文，不能回答成生抽香油凉拌豆腐。
3. 火星麻婆豆腐怎么做？——应提示未收录/未识别，不编造菜谱。
4. 清蒸鱼怎么做？——应显示确认选项。
5. 复制回复：查看菜谱：清蒸鲈鱼——确认后使用鲈鱼原文。

精确确认后仍通过LLM组织答案，不保证完全无幻觉，必须人工对照原文检查。历史生成的AI做法不再进入已确认单菜的提示词；当前问题和保守收集的用户约束仍保留。过敏/忌口的硬过滤不在本次范围，不能仅凭模型提示视为已经满足硬约束。

模糊指代若无法可靠补全，会请求明确菜名；不靠多菜推荐中的最后一项猜测。尚未实现所有自然语言句式或多目标编排，已覆盖常见“X怎么做/的做法/用料/我想做X/查看菜谱：X”及直接菜名。复杂非模板问题仍可能进入通用流程，不能声称已消除所有误替换。

## 自动试跑（9个目标场景）

```powershell
python benchmarks/run_baseline.py --base-url http://localhost:8000 --model Qwen/Qwen3.8-Flash-Next --top-k 5 --cache-state uncontrolled --queries benchmarks/identity_queries.jsonl --repeat 1 --timeout 240 --trace benchmark_results/trace.jsonl --output benchmark_results/v4_identity1
```

如果目录已有responses.jsonl，换新目录。失败仍会停止；先看错误再决定是否继续。查询集混合真实生成、拒绝替换与澄清，不能将整体平均耗时与v3的5条全部回答直接比较。

状态检查（不调用模型）：

```powershell
python benchmarks/check_identity.py --responses benchmark_results/v4_identity1/responses.jsonl
```

核对状态不等于答案正确。not_found和needs_confirmation返回HTTP200是成功处理业务提示，不代表完成菜谱回答。新增CSV/回答日志字段recipe_status、answer_source、recipe_id、options用于区分；故障则返回503/502或SSE error。未收录提示和澄清不写会话历史/答案缓存；目标已确认的分支不复用旧缓存，以免读回v3错误回答，成功答案仍按原逻辑存历史（不是长期偏好管理）。

## 失败分类

- 无精确/别名匹配：业务提示，不调用LLM，也不自动使用相似菜正文。
- 多版本/多菜/未明确指代：需要确认，不调用LLM。
- 本地资料缺失、不可读、文件名标题错配、原文版本变化：503 catalog_unavailable；SSE发error，不误报未收录，不猜其他菜。
- 模型生成失败：沿用v3的502/流式失败及不缓存机制。

SSE元数据中先发送来源，随后正文仍通过chunk显示；旧前端只显示文本也能完成确认操作。服务故障时HTTP/SSE错误字段可用于未来前端提示细分，目前界面显示通用重试提示。

## 验证

51项离线测试通过：包括之前35项回归与新增16项菜谱目录/身份/选项/隔离/普通HTTP处理器/流式处理器测试。使用实际原文验证宫保鸡丁包含熟花生，不混入土豆复炸；缺失目录、错配标题、原文变更均阻断；确认分支不访问旧语义缓存/混合检索。Web层仍使用Flask接口替身，无真实数据库、Flask客户端、模型或浏览器集成测试。

待用户部署后验证真实回答、状态及Trace。此次没有填造质量得分或速度提升百分比。最后一轮v3结果保留，后续准确率对比应区分“正确回答”“正确澄清”“正确提示未命中”和“服务失败”。
