# v10.2：复杂问题分析的分类重试

前提：已经安装v10.1。本包为v10.1增量，不用于原版/v7直接升级。
只改变语义分析阶段的恢复机制，不改变菜谱来源校验、限制条件范围、简单用量捷径或最终生成阶段重试策略。

## 行为

一次复杂问题分析最多两次SDK请求（初次+一次恢复），共享总等待预算，SDK max_retries始终为0。
- 临时连接异常、超时、408/409/429和5xx：预算允许时等待后重试一次。
- 401/403/400/404/422等其他4xx：不自动重试。
- 429若明确是insufficient_quota/billing_hard_limit_reached：不自动重试。
- 格式问题：先只做受控本地JSON解析，支持完整的Markdown json代码围栏。不会使用eval、补造字段、猜测意图或执行输出。
- JSON/字段不合法：如仍有第二次机会，请模型对同一问题修正一次，保留原系统指令和问题。修正请求也占最多两次的名额；前一次若已用于连接重试，不再发第三次修正。
- 模型正常返回clarify，或正常判断后因目标/阈值需要澄清：不当成服务故障重试。
- 未知程序异常、配置错误：不盲目重试。

## 默认预算

总等待预算：25秒；单次最多：15秒；普通临时错误退避：0.2秒。
例如首次等待15秒超时，剩余约9.8秒用于第二次，不会重新再等完整15秒。
服务器返回数值Retry-After时不得提前重试；若超过剩余预算则结束，不为等待服务器突破预算。日期形式Retry-After保守不自动重试。

可选环境变量（不设置即可使用默认）：
- QUERY_ANALYSIS_BUDGET_SECONDS=25
- QUERY_ANALYSIS_ATTEMPT_SECONDS=15

预算只覆盖问题分析，不包括最终回答生成。网络SDK读取超时不总等同墙钟超时，因此额外限制调用方的本地等待；超时后的远端请求不能保证已被取消，可能继续消耗配额。迟到结果只进入独立队列，不写会话、不更新菜谱、也不追加到已完成Trace。每个分析流程仍至多发出两次请求。
不使用阻塞退出会等待后台线程的线程池。请求量大时后台请求及并发资源控制仍需后续压测，本包不宣称已解决高并发容量问题。

## 失败后

- 保留当前菜谱与已设置要求，不把服务故障当作用户换话题。
- 正常分析恢复后继续原取材/生成流程。
- 两次均失败或预算用完才返回analysis_unavailable；临时失败retryable=true，认证/参数/配额/配置等retryable=false。
- Trace记录query_analysis_attempt/result/retry，最后语义分析不可用会标记请求failed。不会把错误提示写成成功回答缓存。
- 错误文本不包含密钥、认证头或模型原始输出；已有监控只记录类型/状态/耗时/usage。
