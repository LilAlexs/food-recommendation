# v9：在 v7 上修复上下文来源与自然表达衔接

## 简单结论

原版不是没有检索到正确菜谱，而是融合时按菜谱node_id去重，把同一菜谱的不同内容块误删。宫保鸡丁简介先进入，正确基本信息和步骤块被删；干煸仔鸡步骤被保留。生成时又未附上元数据中的菜名，模型把其他菜的做法套给目标菜。历史问答整体用于向量检索还会让新菜问题偏回旧话题。

依据：用户2026-10-26上传context_origin.jsonl的4轮真实诊断；4轮缓存均未命中，四道审计菜谱的步骤未发现跨菜共享。只对本次样本下结论，不代表全库完整无误。

## 本包改了什么

这是从v7安装的累积增量包，包含v8的会话身份衔接修复，不需要先安装v8。不是完整项目，不要整目录删除后替换，不要安装到原版备份。

1. hybrid_retrieval：按所属对象+完整正文哈希区分不同内容，保留同一菜的多个信息块；双层结果也不再只按node_id去重。
2. intelligent_query_router：组合结果不再只比较正文前100字符，避免前缀相同而后续步骤不同的片段被误删。
3. generation_integration：普通/SSE统一给每段资料添加来源标签；历史答案不是事实来源，缺什么说明什么，不以“简化版”编造缺失步骤。
4. 延续v7的目标菜谱原文、图身份绑定和原文投影策略，确认的单菜不走通用混合候选；因此不会只靠修去重来防串菜。
5. 引入query_understanding：明确规则命中不额外调用模型；规则无法确认的口语表达，调用一次结构化语义分析（15秒超时、零SDK重试、256输出tokens）。只传当前问题、已确认菜身份、近3轮用户问题（单条最多500字），不传旧AI回答作为事实。
6. 模型输出仍须经过菜谱库确认。猜出的非原话菜名仅作为待确认选项；多义/低置信/分析失败不冒充“库里没有”，而是请求澄清。清蒸鱼等既有版本选择仍优先，不增加调用。模型自报置信度不是校准后的正确率，不保证任意表达均识别成功。
7. 新的通用检索使用当前问题和用户限制，不嵌入旧AI回答；含历史的通用查询不复用答案缓存。确认单菜仍保留原始用户表达和约束用于生成。
8. 包含v8的成功回答才提交当前菜谱身份、连续追问、失败/未确认后清理身份，不仅补“腌多久”字样。

如果v7后端已经运行，合并代码后执行：

